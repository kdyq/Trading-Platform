# 容量与多校演进路线

当前能力面向单校试运行。数据库包含学校和校区，但公开市场允许跨校浏览，后台权限主要是全局角色；它不是已实现的多校隔离平台。扩大到不同学校前须先实现并验证学校范围授权，不能仅靠前端筛选。

## 扩大运营前的边界

用户校园身份、商品、订单、会话、举报和审核任务的学校关系需要明确。管理员增加授权学校范围，默认查询必须与该范围求交；全局管理员权限单独审计。商品双方跨校交易、公共商品可见性、转校/身份过期规则由组织方先确认。

学校边界由服务端查询、对象授权和实时订阅共同执行，并覆盖后台导出、聚合、搜索及私有材料。迁移旧数据前验证学校关系完整，无法确定的数据留在受限队列。先在一所学校启用、观察拒绝日志，再逐校放开；回滚时关闭新增学校入口并保持数据归属。

## 按指标演进

| 能力 | 采用门槛 | 迁移风险与验证 | 回退 |
| --- | --- | --- | --- |
| 共享对象存储/CDN | 本地磁盘接近预算，或需要多实例；公共图片流量持续成为瓶颈 | 先实现适配器，逐对象复制并核对原图/缩略图哈希、权限和旧引用；CDN仅缓存允许公开的资源 | 保留旧对象与映射，关闭新写入后回到旧适配器；不能依赖已过期私密缓存 |
| 多 API 实例 | 优化已确认慢点后仍持续超过体验目标、CPU/连接预算或可用性要求 | 验证共享数据库/对象、Redis广播、一次性票据、限流和任务协调；真实代理下做故障和重连测试 | 缩回一个经验证实例，保持业务事实及对象不变 |
| 任务队列 | 导出、通知、清理积压连续超过处理目标，或占用请求线程/进程 | 引入幂等任务、租约、重试和死信；数据库事实先提交，消费后可重建 | 停止新队列消费者，在幂等边界切回原 worker，不双写双执行 |
| 搜索引擎 | 实际搜索 P95/匹配质量仍不达标，且 PostgreSQL 索引/查询优化已验证不足 | 索引只含允许公开数据；数据库最终校验可见性，防止下架、校园边界和权限延迟泄漏 | 关闭搜索入口切换，回到数据库搜索；索引可重建 |
| 读副本 | 已测得读取成为数据库瓶颈，复制延迟满足目标 | 授权、会话、订单、处罚与写后读仍访问主库；演练延迟与故障 | 把读流量切回主库并限制并发，监控连接预算 |
| 在线支付 | 组织方确认资质、交易责任、退款/争议规则、服务商与成本，且线下交易已有稳定证据 | 单独设计账务、幂等回调、对账、签名、防重放和退款；从沙箱验证开始 | 保留线下交易入口，关闭新支付订单，已有资金按对账流程处理 |

## 容量与人员

容量计划同时记录活跃用户、商品/图片量、日交易、消息速率、峰值在线、审核积压、申诉时限、客服负荷和备份耗时。API/数据库瓶颈与审核、客服人力分别预算；技术扩容不能替代权限训练、值班与反馈流程。

本机性能数据只能作为当前版本的回归参考，不能外推线上人数。每次扩大前，使用真实拓扑和合成数据按预计峰值及突发组合测量 P50/P95、错误率、连接/内存、对象吞吐和 WebSocket 扇出，并演练 Redis、主机和存储故障。

## 演进检查与退出

每次变更须具备负责人、输入确认、数据兼容、备份、停止条件和回退验证。命令由实际平台确定，不预先创建资源：

```text
<capacity-runner> --environment <preproduction> --scenario <approved-synthetic-load>
<storage-migration-tool> --source <old-location> --target <new-location> --verify-hashes
<traffic-switch-tool> --target <approved-version> --scope <approved-school>
```

发现跨校越权、恢复不一致、关键交易持续失败或值班不足时暂停扩大入口，保留现有业务数据，回到已验证的单校范围。没有触发指标与负责人确认时保持现有基础设施。
