# 第十阶段任务 2：隔离性能基线

2026-09-29 在 Windows 11、Python 3.12.5、PostgreSQL 18.6 上执行 `cd backend; python -m scripts.performance_stage10 --output ../docs/第十阶段性能数据.json`，并用不同输出文件再跑一次。脚本创建并删除独立 `test_gate_*` schema；写入 2,000 件商品（其中 100 件待审）、500 条聊天消息和 1 名买家、1 名卖家，随后对相关表执行 `ANALYZE`。单 ASGI 进程，HTTPX 进程内传输。读场景并发 8、下单并发 4；每个单项读场景 20 次，下单 12 次；混合场景并发 8，含首页/搜索/详情/聊天/审核队列各 8 次及新建订单 4 次。测试顺序与构成由脚本固定，使用隔离账号和数据。

原始数据保存了真实接口执行 SQL 的 `EXPLAIN (ANALYZE, BUFFERS)`：首页汇总 4.266 ms；关键词搜索计数 3.492 ms、排序列表 5.155 ms；商品详情 0.234 ms；聊天历史 0.223 ms；待审队列计数 0.089 ms、排序列表 0.181 ms；下单商品行锁查询 0.048 ms、幂等键查询 0.017 ms。它们是从接口实际执行的 SELECT 和参数中捕获并在同一 schema 重放，覆盖计数和列表两条路径。下单期间另按实际 SQL 调用测得商品行锁查询 P95 10.42 ms（12 次）、订单查询 P95 7.26 ms（24 次）、`INSERT ... ON CONFLICT` P95 13.05 ms（12 次）；第二轮分别为 4.90/4.75/7.60 ms。写入 SQL 只记录实际执行时长，没有在完成后用 `EXPLAIN ANALYZE` 重放，以免产生重复写入。接口 P95 明显高于单条数据库执行时间，当前小样本下没有证据支持立即增加索引或私密内容缓存。商品、消息、订单和举报索引及分页边界已复核；授权结果、私聊正文没有新增缓存，关键业务事实仍以 PostgreSQL 为准。

依据两次样本暂定本机回归阈值：8 并发普通读/混合 P95 < 900 ms，聊天历史 P95 < 1,200 ms，4 并发下单 P95 < 500 ms，错误率 0%；两次样本均达到此**新阈值**。阈值为试运行前的本地门禁，需要组织方结合真实体验要求确认，并在真实拓扑和预计用户量确定后重测。进程内传输没有网络、TLS、反向代理、多实例或真实用户分布，也未测 WebSocket 扇出和 Redis 故障时的吞吐量；因此不能外推线上容量。后续超阈值时先捕获实际慢查询计划、连接和内存峰值，再决定优化。
