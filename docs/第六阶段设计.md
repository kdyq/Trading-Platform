# 第六阶段私聊、通知与隐私保护设计

## 1. 范围与成功标准

本阶段只实现开发文档第六阶段：商品上下文会话、持久消息、可靠实时推送、聊天界面、站内通知、屏蔽与聊天举报。订单创建、人工审核处置和举报后台属于后续阶段；聊天页只展示“发起订单”入口及未开放说明，不提前实现订单状态机。

成功标准是两个已登录且校园认证有效的真实浏览器用户能够围绕公开有效商品唯一建聊，完成幂等发送、实时接收、历史补拉、未读与已读、刷新和断线恢复，并能屏蔽或举报；任何页面、接口和推送都不暴露登录邮箱、校园邮箱、手机号、私聊正文通知摘要或内部审核资料。四个任务分别形成独立提交，最终通过 PostgreSQL、Redis 降级、前后端和双浏览器验收。

## 2. 方案比较与选择

推荐并采用“PostgreSQL 事实源 + Redis 瞬时分发 + REST 补拉 + 本地连接中心”方案。消息必须先在数据库事务中落盘，事务提交后才向当前实例连接和 Redis 频道广播；客户端按消息游标去重，重连后从 PostgreSQL 补拉。Redis 不保存唯一消息副本，短暂故障只降低跨实例实时性和在线态，已提交消息仍可通过 REST 恢复。

备选一是只用进程内 WebSocket 中心，实现最简单，但多实例会漏实时事件且无法满足阶段要求。备选二是 Redis Streams 或独立消息队列承担消息主链路，可靠性强但会引入消费者组、重放和双写一致性，本阶段试运行规模不需要。推荐方案保持数据库一致性边界清楚，也为以后替换分发设施保留接口。

浏览器 WebSocket 不在 URL 直接携带访问令牌。已认证 REST 接口签发短时、单次使用的随机连接票据，Redis 可用时票据跨实例消费；Redis 不可用时明确返回实时服务暂不可用，用户仍可使用 REST 查看与发送，页面展示离线/降级状态。

## 3. 任务 1：会话与持久消息 API

沿用现有 `conversations` 和 `messages`，补充必要字段与约束。会话保存商品标题、价格和缩略图标识的最小快照；当前商品状态仍从商品表读取，所以下架或售出后历史可查看但会明确标记不可继续交易。新增会话已读状态表，以 `(conversation_id, user_id)` 唯一记录最后已读消息和时间。消息使用 `(created_at, id)` 键集游标，正文数据库约束为 1–2000 字符，`(sender_id, client_message_id)` 保证重试幂等。

只有校园认证有效的买家可以从当前可见且可沟通的商品建聊。卖家由商品事实决定，买卖双方不能相同；仓储以 PostgreSQL 冲突忽略/回读处理并发建聊。会话列表只查询本人为买家或卖家的记录，一次返回对方公开昵称、最小商品上下文、最后消息时间、未读数和当前商品状态，不返回正文预览之外的敏感资料；列表有界。历史和发送接口再次验证参与者身份与屏蔽关系。

发送先锁定会话/校验参与者与屏蔽，再按幂等键插入消息、更新会话时间并创建不含正文的聊天通知。重复键且正文一致返回原消息；同键不同正文返回 409。已读只允许推进到本会话内实际存在的消息，不允许回退或引用其他会话。

## 4. 任务 2：WebSocket、重连与降级

REST `POST /chat/ws-tickets` 签发有效期一分钟、单次消费的随机票据；`/api/v1/chat/ws` 在升级前消费票据并绑定用户。连接建立后只自动订阅本人有权访问的用户频道，不接受任意会话 ID 订阅。服务发送 `ready`、`message.created`、`conversation.read`、`notification.created`、`pong` 和结构化错误事件。

持久消息和已读事件在事务提交后发布。应用维护当前实例的用户连接集合；Redis 发布订阅用于跨实例转发，事件含稳定 ID，客户端使用消息 ID/事件 ID 去重。心跳由客户端周期发送 `ping`，服务回复 `pong`；断线采用指数退避并带随机抖动。恢复时客户端先重新取会话列表，再以最后消息游标补拉当前会话。

消息发送仍走幂等 REST API，WebSocket 负责低延迟推送，从而避免“Socket 显示成功但数据库尚未提交”。超大消息由 REST 校验拒绝；按稳定用户 ID 与会话 ID 做发送频率限制。Redis 不可用时票据接口返回稳定 503，REST 写入和查询继续可用，页面显示“实时连接不可用，消息仍会保存，可手动刷新”。

## 5. 任务 3：聊天界面

新增 `/messages` 和 `/messages/:conversationId`。桌面端为会话列表与聊天窗双栏，移动端为单栏路由切换；复用现有米白背景、白色圆角卡、汽水橙主操作和棕色文字。会话项展示商品缩略信息、对方公开昵称、时间与未读角标；聊天头部展示当前商品状态与最小上下文，不展示任何邮箱或手机号。

消息气泡为本人橙底白字、对方白底描边，按本地日期分组。发送状态只有“发送中、已保存、失败可重试”，收到服务端消息后以 ID 合并，重试复用原 `client_message_id`。进入会话后定位首条未读并推进已读位置。输入框支持 Enter 发送、Shift+Enter 换行，发送后恢复焦点，所有按钮和连接状态具有屏幕阅读器标签。

安全提示固定表达为“请勿提前转账，尽量在平台内沟通并保留争议证据”，不承诺未确认的处理时效。商品失效时保留历史聊天但禁用“发起订单”，聊天是否还能继续由后端商品/屏蔽策略决定。长文本断行、空状态、断线提示与失败重试在 375、768、1024、1440 视口验收。

## 6. 任务 4：通知、屏蔽与反骚扰

新增站内通知、投递尝试、通知偏好和用户屏蔽表。通知以 `(recipient_id, event_key)` 唯一去重，类型覆盖聊天、商品审核、订单、举报结果；本阶段实际产生聊天通知，其余类型保留明确枚举和服务入口供后续阶段调用。通知只保存通用标题、结果摘要与站内目标，不保存私聊正文、认证材料或内部备注。读取、未读计数、单条/全部已读和分类偏好均按接收者隔离。

站内投递写入通知即为可恢复事实，投递尝试记录状态、次数、错误摘要和下次重试时间；重试命令按稳定事件键执行，不重复生成通知。WebSocket 推送失败不改变站内通知事实，下一次列表请求仍可获取。

屏蔽以 `(blocker_id, blocked_id)` 唯一，禁止自我屏蔽。任一方向存在有效屏蔽时，双方都不能新建会话或发送新消息，但历史消息和举报证据保留。聊天举报复用现有 `reports`，目标锁定具体消息，验证举报人属于该会话；原因使用稳定代码，说明长度受限，重复举报由现有唯一键合并。

反骚扰边界提供可替换的风险钩子，默认不编造敏感词清单；确定执行正文长度、空白、控制字符、链接数量和稳定用户/会话频率限制。命中策略返回稳定 422/429，日志只记录规则代码、用户和会话标识，不记录正文。

## 7. 数据一致性、安全与隐私

- PostgreSQL 是会话、消息、已读、通知、屏蔽与举报的唯一事实源。
- 所有读取按参与者或接收者条件查询；不存在与无权访问统一返回 404，避免枚举。
- 校园认证、账户状态、商品状态、屏蔽和频率限制均以后端为准。
- 客户端幂等键限制长度与字符集；服务端不相信发送者、卖家、未读数或时间字段。
- WebSocket 票据单次、短期、随机且不写日志；访问令牌不放入 Socket URL。
- 推送和通知不包含私聊正文；日志、错误和审计数据同样不包含正文。
- 数据保留与账号注销的完整法务策略属于第十阶段，本阶段不物理删除历史证据，也不虚构保存期限。

## 8. 实现与验证顺序

1. 扩展迁移、会话仓储、持久消息、已读与幂等 API；运行权限、并发和游标 PostgreSQL 测试，提交任务 1。
2. 实现短时票据、本地连接中心、Redis 发布订阅、提交后广播、心跳与降级；运行 WebSocket/Redis 集成测试，提交任务 2。
3. 实现响应式聊天页、重连补拉、发送状态、未读定位和安全提示；运行前端测试、无障碍检查和四视口双浏览器流程，提交任务 3。
4. 实现通知、偏好、投递审计、屏蔽、举报与风险钩子；运行服务、权限、并发和浏览器测试，提交任务 4。
5. 运行统一 PostgreSQL/Redis 门禁、迁移往返和独立深度审查，修复阻断项后停在第六阶段。

## 9. 自审结论

- 文档无 TBD、TODO 或依赖后续人工选择的占位要求。
- 四个任务边界与开发文档一致，没有提前实现订单、审核后台或真实外部通知渠道。
- 消息提交、广播和补拉顺序明确，不存在未持久化消息显示为成功的路径。
- Redis 降级、幂等、权限、屏蔽、隐私和日志边界均有明确后端规则。
- UI 复用现有设计系统，未引入与核心页面长廊冲突的独立视觉语言。
- 根据用户已授权的后续文档自动批准规则，本设计在自审通过后直接进入实现。
