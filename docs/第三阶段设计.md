# 第三阶段账户与校园认证设计

## 1. 范围与成功标准

第三阶段覆盖普通账户注册、登录邮箱验证、访问令牌、刷新令牌轮换、退出、找回密码、个人资料、设备会话、校园邮箱认证和人工申诉。普通账户与校园认证保持独立，未认证用户只能浏览。

成功标准如下：

1. 安全测试覆盖弱密码、重复邮箱、验证码过期与尝试耗尽、用户枚举、刷新令牌重放、停用用户、重置令牌单次使用和越权访问。
2. 前端覆盖注册、登录、找回密码、个人中心、账户安全和校园认证的加载、空态、成功与错误状态。
3. 校园认证前，发布、私聊、下单和评价统一返回 `campus_verification_required`。
4. 敏感值不进入日志、响应、Git 或公开存储路径。

## 2. 方案选择

采用短时 JWT 访问令牌与数据库持久化刷新会话组合：访问令牌只承载用户、会话、签发与近期认证时间；刷新令牌使用随机不透明值，数据库只保存摘要。每次刷新都会撤销旧会话记录并在同一令牌族创建新记录。再次使用已撤销的旧刷新令牌时，系统撤销整个令牌族。

纯 JWT 无状态会话实现较少，但无法稳定满足退出全部设备、指定会话撤销和重用检测，因此不采用。将全部会话放入 Redis 虽然读写更快，但会使持久审计依赖缓存可用性，也不采用。

## 3. 后端边界

- `core/security.py`：密码哈希、随机令牌摘要、JWT 签发与验证。
- `services/email_verification.py`：Redis 验证码、频率限制、尝试次数和一次性消费。
- `services/mailer.py`：QQ SMTP 邮件发送，网络发送在线程中执行，路由不直接接触授权码。
- `services/auth.py`：注册、登录、令牌轮换、退出与当前用户业务规则。
- `services/account.py`：资料、密码重置和设备会话。
- `services/campus.py`：校园域名规则、状态机、唯一绑定和申诉材料。
- `repositories/identity.py`：身份领域的 SQLAlchemy 查询和事务内写入。

API 通过依赖注入取得数据库、Redis、邮件发送器和文件存储。测试使用内存替身验证业务合同，PostgreSQL 门禁验证迁移与并发唯一约束。

## 4. 安全参数

- 密码：8-128 字符，至少一个英文字母和一个数字，不含空白，使用 Argon2id。
- 登录邮箱验证码：6 位数字，10 分钟有效，60 秒内不得重复发送，单小时最多 5 次，最多尝试 5 次；Redis 只保存带服务端密钥的摘要。
- 访问令牌：15 分钟；刷新令牌：30 天；生产环境刷新令牌写入 `Secure`、`HttpOnly`、`SameSite=Lax` Cookie，本地环境不设置 `Secure`。
- 登录失败统一返回 `invalid_credentials`，密码重置请求无论账户是否存在都返回相同响应。
- 密码重置令牌：30 分钟、单次使用；发送失败时不消耗既有有效令牌。
- 敏感操作近期认证窗口：15 分钟。

## 5. 数据模型

- `users` 增加协议版本、同意时间和头像引用；登录邮箱继续独立唯一。
- `user_sessions` 每一行代表一个刷新令牌版本，保留令牌族、设备摘要、最后使用、过期和撤销时间。轮换产生新行，旧行保留用于重用检测。
- `password_reset_tokens` 保存重置令牌摘要、有效期和消费时间。
- `school_email_domains` 保存学校允许的邮箱域名规则。
- `campus_verification_appeals` 保存申诉状态、说明、私有材料引用和保留期限。

学校、校区和域名均由数据配置。仓库不预置真实或虚构学校资料。

## 6. 校园认证状态机

邮箱验证码确认后由 `unapplied/rejected/expired` 进入 `verified`，并设置认证有效期。到期后变为 `expired`，需要重新认证。邮箱方式不可用时，用户可以提交申诉并进入 `appealing`；当前阶段只提供提交、本人查询和私有材料读取，管理员审核接入留到管理阶段。

同一时间，一个用户只能有一个活动认证；一个校园邮箱只能绑定一个活动认证。数据库部分唯一索引作为并发写入的最终保护，服务层在冲突时返回稳定业务错误。

## 7. 私有材料存储

申诉材料写入 `backend/var/private/campus-appeals/<user-id>/`，数据库只保存不可预测的内部引用。材料没有静态公开 URL；下载必须经过当前用户或审核权限检查。默认保留 180 天，过期清理由后续运维任务调度，当前阶段记录 `retention_until` 并提供可测试的过期判定。

## 8. 前端设计

沿用现有暖纸背景、白色 16px 圆角卡片、12px 输入框、橙色主按钮和绿色信任提示。注册与登录使用同一窄卡结构；个人中心使用身份摘要、业务入口和账户安全分区；校园认证明确分开登录邮箱与校园邮箱。

表单标签始终位于输入框上方，错误位于字段下方；提交时按钮禁用并显示具体动作，成功后提供下一步。移动端单列展示，不加入自动滚动或装饰性动画；所有交互依赖键盘焦点、原生语义和 `aria-live` 状态区。

## 9. 错误合同与审计

业务错误统一返回 `{code, message, request_id}`。认证门禁使用稳定错误码，前端只显示安全的中文提示。请求日志只记录方法、路径、状态码和请求 ID，不记录请求体、密码、验证码、Cookie、Authorization 或完整令牌。

## 10. 验收顺序

1. 后端单元与接口测试。
2. PostgreSQL 迁移、约束与事务门禁。
3. 前端单测、类型、Lint 和构建。
4. 使用真实浏览器完成注册、登录、找回密码、个人中心和校园认证主流程，并检查 375px 与桌面视口。
5. 每个任务独立提交；第三阶段结束后执行全量质量脚本并停止在阶段门禁。
