# 第八阶段信用、举报与商品审核设计

## 1. 范围与成功标准

本阶段只实现开发文档第八阶段：可解释信用流水、商品/用户/聊天/订单举报、私有证据、商品审核队列，以及举报处置、申诉和审计闭环。阶段内复用既有角色表识别 `REVIEWER`、`ADMIN`、`SUPER_ADMIN`，只提供审核所需的最小权限判断；角色初始化、分配、停用和完整权限管理仍属于第九阶段。

成功标准是信用余额能够仅由追加流水重算，重复领域事件不会重复计分；举报人能够提交并跟踪举报而无法读取内部备注；审核员能够并发安全地批准、驳回、隐藏和恢复商品；处罚、申诉、撤销、信用反向流水、通知及审计记录在同一事务边界内保持一致。公开接口不得泄露证据对象键、聊天正文、订单隐私、内部备注或其他用户资料。

## 2. 方案选择

采用“追加式领域流水 + PostgreSQL 状态机 + 最小阶段内审核权限”。信用流水、举报事件和审核记录均不可覆盖；当前余额、公开结果和当前状态是便于查询的投影，任何投影都可由事件重新计算或与事件核对。商品和举报写操作锁定当前行并校验 `version`，高风险动作使用独立权限代码和逐项请求。

不采用直接修改信用分或只保存举报最终状态的方案，因为无法解释、撤销和审计；也不采用完整事件溯源重建所有业务表，因为现有订单、商品和用户仍适合以关系表保存当前事实，全面迁移会扩大风险。批量审批和自动处罚不在本阶段实现，避免在规则与 RBAC 尚未完整运营前引入高风险捷径。

## 3. 任务 1：信用规则、流水与公开边界

信用初始分为 100，规则版本为 `v1`。完成交易双方各加 2 分；收到 4–5 星有效评价加 1 分，1–2 星减 1 分，3 星不记分；确认违规、爽约等处罚由审核决定写入明确分值；管理员纠错只能追加 `moderation_adjustment`，不能改写历史或最终数字。每条流水保存用户、事件类型、来源类型与来源 ID、规则版本、变动值、变动后余额、公开原因、创建者和反向来源。

唯一来源键保证同一领域事件最多记账一次。写入时锁定用户对应的最后流水，按事件顺序计算 `balance_after`；重算按 `(created_at, id)` 稳定排序，从初始分累加并检查每行余额。撤销处罚追加与原记录等值反向流水，引用原流水，绝不删除或改写原记录。争议或举报在确认违规前不产生扣分。

用户可查看自己的余额、规则版本和分页明细；公开市场仅展示等级与区间摘要，不公开分值构成或负面事件细节。订单完成与有效评价在现有订单事务中调用幂等记账服务，保证订单、通知和信用流水共同提交。

## 4. 任务 2：举报、证据与用户进度

统一举报目标为商品、用户、聊天消息和订单。举报包含结构化原因、说明、当前状态和公开结果摘要；内部备注单独保存且永不出现在举报人接口。证据附件只支持 PDF、PNG、JPEG，校验文件签名、声明类型和大小，存放于私有目录；数据库保存随机对象键和元数据。下载必须同时满足举报人读取自己附件或审核角色调查该举报，且响应禁止缓存。

同一举报人对同一目标和原因的未结案举报使用稳定合并键：重复提交返回同一举报并追加去重后的新证据和事件，不吞掉材料。每用户举报创建采用数据库时间窗口计数限制；已存在举报追加证据不受创建限流影响。举报人可以在尚未受理时撤回，并只能看到 `submitted/reviewing/resolved/dismissed/withdrawn/appealed` 等公开状态、自己的说明、证据文件名和公开结果。

举报状态每次转换追加事件，记录操作者、前后状态、公开说明和不对外的审计数据。商品详情、用户相关入口、聊天和订单详情复用统一白色圆角举报对话框；按钮采用白底取消和汽水橙提交，上传进度与安全错误明确可见。

## 5. 任务 3：商品审核队列与处置

审核队列只对审核角色开放，按提交时间和 ID 稳定分页，支持状态筛选。详情展示商品字段、卖家公开摘要和经授权的商品图片，不提供角色、用户删除或审计删除能力。批准仅允许 `pending_review -> on_sale`，写入首次发布时间；驳回仅允许 `pending_review -> rejected`，必须选择原因并填写可公开说明；卖家修改后沿用第五阶段流程重新提交。

隐藏允许审核员将公开商品转为 `hidden` 并保存恢复前状态；恢复仅回到仍然合法的原公开状态，否则回到 `pending_review`。请求必须携带商品 `version`，仓储以行锁与版本比较拒绝过期操作并返回 409，确保两名审核员不会相互覆盖。批准与低风险驳回可逐项调用同一接口；本阶段不提供批量隐藏、批量处罚或删除。

每个决定写入不可覆盖的审核记录和审计日志，保存操作者、理由、前后状态、商品版本和请求 ID，并向卖家发送不含内部信息的审核结果通知。通过后的商品才进入公开市场查询。

## 6. 任务 4：调查、处罚、申诉与撤销

审核员可受理举报、临时隐藏关联商品、驳回举报或确认违规。确认违规必须选择处罚代码、公开结果、内部理由、证据引用和信用变动；普通审核员只能执行警告、内容隐藏和有限信用扣减，暂停用户等高风险动作要求 `ADMIN` 或 `SUPER_ADMIN`。所有权限由后端根据当前数据库角色执行。

处罚以审核决定为幂等来源，同事务写入举报事件、审核记录、审计日志、必要的商品状态、信用流水和双方通知。被举报人只能看到与自己有关的最终决定和公开理由，不得看到举报人身份或私有证据。被处置用户可在结案后一次性申诉，提交说明和可选私有材料；申诉进入独立事件链。

复核默认要求操作者不同于原决定人；`SUPER_ADMIN` 可在只有一名授权人员的开发环境中显式覆盖，但必须填写覆盖理由并留下审计。维持决定会记录结论；撤销处罚会恢复仍允许恢复的商品状态，追加反向信用流水并发送通知，不删除原处罚、原信用项或原审计记录。

## 7. API、错误与前端结构

新增 `/credit` 自助查询、`/reports` 用户举报、`/moderation/products` 商品审核和 `/moderation/reports` 调查/申诉复核 API。稳定错误覆盖：401 未登录，403 校园认证或角色权限不足，404 对象不可见，409 版本/状态/幂等冲突，413 文件过大，422 原因、证据或状态参数无效，429 举报创建过频。

前端新增信用页、我的举报页和审核工作台，并在商品、聊天、订单入口接入统一举报对话框。管理工作台沿用浅暖背景、白色卡片、紧凑筛选和橙色关键操作；界面隐藏无权操作仅是体验优化，所有授权以服务端为准。通知摘要只包含目标类型、处理状态和公开说明，不包含证据、内部备注或私聊正文。

## 8. 实施顺序与验收

1. 扩展信用模型和迁移，实现规则服务、自助明细、订单/评价幂等计分、重算与 PostgreSQL 并发测试，形成任务 1 提交。
2. 扩展举报事件与私有证据，实现统一举报 API、合并/限流、自助进度和举报对话框，完成文件与浏览器测试，形成任务 2 提交。
3. 实现最小审核角色校验、商品审核队列、并发版本控制、处置记录、卖家通知和后台页面，完成状态机与双审核员 PostgreSQL 测试，形成任务 3 提交。
4. 实现举报调查、处罚权限、申诉复核、撤销恢复、反向信用和通知闭环，完成端到端权限、审计和浏览器测试，形成任务 4 提交。

最终运行 Ruff、mypy、后端测试、Alembic 全量升降级、PostgreSQL 专项、前端类型/格式/单测/构建及第八阶段浏览器门禁；按风险调用只读 reviewer 检查要求、差异、执行路径和测试证据，修复重要问题后停止，不进入第九阶段。
