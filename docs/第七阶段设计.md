# 第七阶段订单、面交与评价闭环设计

## 1. 范围与成功标准

本阶段只实现开发文档第七阶段：线下付款订单、卖家接受与商品预留、校内面交预约、取消和超时、卖家交付与买家确认、争议冻结、订单中心及双向评价。平台不经手资金，不创建支付单、收款码、物流或自动退款；争议只进入待处理队列，后台裁决属于后续阶段。

成功标准是两个已登录且校园认证有效的真实浏览器用户能够从商品或聊天发起订单，卖家接受并原子预留商品，双方确认面交安排，完成交付与收货确认，再在完成后三十天内各评价一次。任一非法状态、越权操作、重复命令、并发接受或超时任务都由后端拒绝或幂等合并，不能只依赖前端禁用按钮。

## 2. 方案选择

采用“PostgreSQL 状态机 + 事务事件日志 + 可抢占后台任务”。`orders` 保存当前事实和必要快照，`order_events` 追加每次状态变更，服务层集中定义允许转换；数据库行锁、部分唯一索引和版本字段承担并发边界。定时任务使用 `FOR UPDATE SKIP LOCKED` 抢占到期订单，重复运行只会看到已终态记录并安全跳过。

没有采用完整事件溯源，因为现阶段查询、迁移和后台裁决都不需要以事件重建全部订单，复杂度明显超过收益；也不采用各接口直接更新若干字段的方案，因为它难以保证商品、订单、通知和事件的一致提交。

## 3. 订单模型与幂等

订单状态为：`pending_seller_confirmation`、`accepted`、`scheduled`、`seller_delivered`、`completed`、`cancelled`、`expired`、`disputed`。创建订单只允许认证买家针对自己的校区内 `on_sale` 商品发起，金额始终取数据库商品价格。订单保存商品标题、成交价、校区名称、买卖双方公开昵称和线下付款方式快照，不保存邮箱或手机号。

同一商品可以同时存在多个待卖家确认请求；卖家接受时锁定商品和目标订单，只有商品仍为 `on_sale` 才能成功。成功接受会把商品原子改为 `reserved`，并将该商品其他待确认订单取消为“商品已被其他订单预留”。部分唯一索引只允许一个 `accepted/scheduled/seller_delivered/disputed` 活跃预留订单；同一买家对同一商品只能有一个未终结请求。

创建使用 `(buyer_id, idempotency_key)`；其他写操作携带 `client_action_id`，由订单命令表记录操作者、动作、载荷摘要和结果事件。同键同载荷返回当前事实，同键不同动作或载荷返回 409。状态转换与事件、通知和商品状态在同一事务中完成。

## 4. 面交预约、取消与过期

面交候选使用独立提议表，记录提议人、时间、校内地点文本、双方确认时间和状态。提议人自动确认，另一方确认后提议生效，订单进入 `scheduled`；改期创建新候选，在双方确认前保留原已确认安排，生效后旧安排标记为已替代。地点仅出现在订单详情和双方授权接口中，列表、通知和日志都不包含地点。

待卖家确认订单二十四小时后过期；过期任务每批行锁抢占，转为 `expired` 并写事件和无敏感信息的通知。`pending/accepted/scheduled` 可由任一方取消并记录结构化原因；若订单已预留，取消或过期与商品恢复 `on_sale` 在同一事务完成。`seller_delivered` 后不再允许普通取消，只能确认完成或发起争议。

## 5. 交付、完成与争议

采用双方确认规则，不使用短信或短期确认码。卖家在已接受或已排期订单上标记已交付，订单进入 `seller_delivered`；只有买家可以确认收到，随后订单与商品在同一事务分别进入 `completed` 和 `sold`，记录完成时间和订单事件。重复提交由命令幂等返回，不重复写事件或通知。

任一方可在 `accepted/scheduled/seller_delivered` 状态发起争议，订单进入 `disputed` 并保存最小原因代码和可选说明；详细说明不进入列表或通知。争议状态禁止自动过期、完成和评价，等待后续授权后台处理。

## 6. 订单中心与评价

新增 `/orders` 和 `/orders/:id`。订单中心使用“买入/卖出”胶囊切换和状态筛选，游标按 `(updated_at, id)` 稳定分页；卡片只显示商品快照、对方公开昵称、金额、状态和更新时间，不显示预约地点。详情展示允许操作、当前预约、商品信息和追加式事件时间线。

完成订单后双方在三十天内各评价一次。评分为 1–5，标签从固定集合选择，文本单独限制长度；评价对象必须是订单另一方。评价保存可见状态，市场统计仅聚合 `completed` 订单上的可见评价，因此隐藏评价会自然从实时重算结果中移除，不维护易漂移的冗余平均分。

## 7. API、通知与错误

订单 API 覆盖创建、列表、详情、接受、预约提议与确认、取消、交付、收货确认、争议和评价。认证、校园认证、对象级参与者权限和状态机验证统一在服务层执行。稳定错误包括 403 权限/认证门禁、404 不可见资源、409 状态或幂等冲突、422 参数与时间边界错误。

订单创建、接受、排期、取消、过期、交付、完成、争议和评价均使用 `(recipient_id, event_key)` 生成不含地点、评价正文或争议说明的站内通知，并复用第六阶段可恢复投递流程。

## 8. 实施顺序与验收

1. 扩展订单数据库、创建/接受状态机和并发预留，完成 PostgreSQL 并发与权限测试，形成任务 1 提交。
2. 实现预约、取消、过期抢占任务和通知，完成时间边界及任务重复执行测试，形成任务 2 提交。
3. 实现卖家交付、买家确认、争议冻结和事件证据，完成状态机与幂等测试，形成任务 3 提交。
4. 实现订单列表/详情、双向评价、实时聚合和双浏览器全生命周期门禁，形成任务 4 提交。

最终运行 Ruff、mypy、后端测试、Alembic 全量升降级、PostgreSQL 专项、前端类型/格式/单测/构建和双浏览器 Playwright 门禁；完成风险分级双审查后停止，不进入第八阶段。
