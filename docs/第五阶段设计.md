# 第五阶段商品发布、图片与收藏闭环设计

## 1. 范围与成功标准

本阶段只实现开发文档第五阶段：分类与校区基础数据、商品图片处理、卖家商品状态机、PostgreSQL 搜索增强和收藏闭环。聊天、订单、审核后台与信用计算仍属于后续阶段，不在本阶段提前实现。

成功标准是认证用户能够创建和恢复草稿、上传并排序图片、提交审核、撤回/下架/标记售出，以及收藏公开商品；所有写操作经过服务端身份、校园认证、所有权、版本和状态校验。四个任务分别形成独立提交，最终通过 PostgreSQL、前后端测试和四档真实浏览器验收。

## 2. 方案比较与选择

采用“数据库事实源 + 图片临时区两阶段确认 + 显式状态机 + 乐观并发版本”的方案。商品草稿始终写入数据库；图片上传先生成独立临时记录和随机对象键，保存商品时在同一数据库事务内确认归属，提交成功后再移动对象；版本不匹配返回冲突，重复提交在目标状态已达成时幂等返回。

未采用仅浏览器本地草稿方案，因为跨设备、刷新和并发编辑无法可靠恢复。未采用上传后立即写入永久目录方案，因为事务失败会留下难以归属的文件。未采用 Elasticsearch 或独立任务队列，因为试运行规模用 PostgreSQL、同步图片处理和可执行清理命令即可满足阶段目标。

## 3. 任务 1：分类与校区基础数据

分类增加规范化 `slug`、父级、自身层级、排序和启停约束；校区沿用学校归属、代码、排序和启停，并补充非负排序约束。父分类最多两层，不能引用自身；停用只影响新发布选择与公开筛选，不删除历史引用。

公开目录接口只返回启用且未删除的学校、校区与分类树。管理读取接口保留停用历史数据，并要求管理员权限；变更通过数据库 `version` 防止覆盖，并使进程内短期缓存失效。开发种子只写项目已有的演示分类，不生成学校或校区正式资料；命令按稳定代码 upsert，可重复执行。

## 4. 任务 2：图片处理与存储生命周期

存储边界定义为对象存储协议，提供本地文件实现和 S3 兼容实现。本地实现只接受由服务生成的相对对象键并验证解析后仍位于根目录；S3 实现通过注入的 S3 客户端调用标准对象 API，业务层不依赖厂商扩展。

上传只接受 JPEG、PNG 与 WebP。服务同时检查文件签名、Pillow 解码、像素数、单文件大小和每用户临时图片数量；所有图片重新编码以移除 EXIF，并生成固定最大边长的缩略图。SVG、损坏内容、扩展名伪装、路径穿越和超限均被拒绝。

`product_image_uploads` 记录临时/已确认/已删除状态、所有者、随机对象键、尺寸、媒体类型和过期时间。数据库状态而非目录前缀是对象生命周期的事实源；商品保存事务以同一对象键原子确认图片归属，不在提交边界移动对象。这样进程在提交前中断时记录仍为可清理临时状态，提交成功后同一对象立即成为受商品引用的持久对象，不存在数据库与对象移动之间的崩溃窗口。清理命令只删除超过安全窗口且仍为临时状态的对象。商品删除只软删除图片记录并按保留期清理，不立即破坏历史证据。

## 5. 任务 3：草稿与发布状态机

商品字段为标题、描述、价格、原价、分类、校区、成色、可议价、交付说明和图片。草稿允许不完整保存；提交审核时执行完整校验，至少一张图片、启用分类、启用校区且校区属于卖家当前有效认证。

允许的卖家转换为：`draft -> pending_review`、`pending_review -> draft`（撤回）、`rejected -> draft`、`on_sale/reserved -> hidden`、`on_sale/reserved -> sold`、`hidden -> pending_review`。卖家不能直接进入 `on_sale`。审核状态的实际批准/拒绝属于第八阶段；本阶段用状态机和测试确保不能绕过。

编辑携带 `version`，仓储更新使用行锁和版本比较；版本过期返回 409。审核中禁止直接编辑，必须先撤回。草稿保存与提交按钮均禁用重复请求；达到目标状态后的同一提交返回当前资源，不产生第二次转换。

前端提供三步发布页：基本信息、图片与交付、确认提交。每次字段变化防抖保存本地恢复副本；已有服务器草稿优先，冲突时提示重新载入。认证和校园认证门禁在进入页面及服务端写接口同时执行。

## 6. 任务 4：搜索与收藏

公开搜索继续使用参数化 SQL，关键词同时匹配标题与描述，保留分类、校区、价格、成色、可议价、状态和排序。稳定排序均以商品 ID 作为最终游标；为公开状态、发布时间、分类/校区与价格组合补充与真实查询一致的索引。代表性 PostgreSQL 查询执行 `EXPLAIN` 并记录计划，不引入 Elasticsearch。

收藏使用数据库唯一约束 `(user_id, product_id)`。新增采用冲突忽略，删除采用精确用户和商品条件，因此重复操作均幂等。收藏列表只返回当前仍可见商品；停用或下架商品不泄露详情，但历史收藏记录可保留。商品摘要返回收藏数，登录用户额外得到本人是否已收藏；列表查询使用聚合/相关子查询一次取回，避免逐商品查询。

## 7. 安全、错误与可观测性

所有写接口要求有效访问令牌和正常账户；发布管理还要求未过期校园认证。404 用于隐藏不属于当前用户的商品，409 用于版本或状态冲突，422 用于字段与图片校验，413 用于文件超限。响应不返回对象键、临时路径、校园邮箱或内部审核字段。

图片访问继续经受控 API 解析，不开放存储目录。生产环境文档区分公开商品派生图与私有临时原图；对象存储凭据只从环境变量读取。清理命令输出计数，不输出文件内容、令牌或凭据。

## 8. 实现与验证顺序

1. 数据约束、分类树、目录管理读取、缓存失效与幂等种子，运行迁移/服务/API 测试并提交任务 1。
2. 图片记录、存储协议、本地/S3 兼容实现、真实图片处理、临时确认与安全清理，运行图片单元/集成测试并提交任务 2。
3. 商品草稿 API、状态机、三步发布页、自动恢复、并发和权限测试，运行真实浏览器发布流程并提交任务 3。
4. 搜索索引与查询、收藏 API/列表/计数、详情收藏交互和 PostgreSQL `EXPLAIN` 基线，运行收藏浏览器流程并提交任务 4。
5. 运行统一质量门禁、数据库迁移往返和 375/768/1024/1440 浏览器验收；修复审查发现后停在第五阶段。

## 9. 自审结论

- 文档没有 TBD、TODO 或依赖后续人工选择的占位要求。
- 四个任务边界与开发文档一致，没有提前实现聊天、订单或后台审核。
- 数据库、文件系统与事务边界明确，图片失败可补偿、临时对象可安全清理。
- 权限、所有权、状态、版本、幂等和公开可见性均由服务端强制执行。
- 方案在试运行规模内保持简单，并为后续 S3、审核与订单阶段保留稳定接口。
